# TextTool 2.4.5 发版收口设计

> 日期：2026-08-03 ｜ 状态：已收口（2026-09-29） ｜ 类型：设计文档（仅方案，不实施）
> 收口结论：B1 已随 v2.6.1 落地；A1/A2 于 2026-09-29 落地并随 **v2.6.2** 发版（实际根因与本文假设不同，见 §7）；

> 来源：2.4.4 发布实测暴露的收口问题 + 发布流程痛点（本文档即该组问题的权威记录）
> 前置事实：2.4.4 为首个 ECDsa 签名发布版本（zip + .sha256 + .sig 三件套），发布流程见 doc/UpdateSecurity.md

## 1. 背景与目标

2.4.4 落地了自更新安全架构（离线签名 + 主机白名单 + 禁重定向 + 严格版本校验），但发布实测暴露出 3 类收口问题：

1. **S302 类代理下 zip 下载超时**（约 30s 触及 30s 超时失败）
2. **替换脚本 wait-loop 脆弱**（PID 复用竞态 + GNU timeout 遮蔽导致无限空转）
3. **发布流程半手工**：下载 CI 产物 → 离线签名 → 上传 .sig → 自检，每步都是敲命令，易遗漏检查清单项

另有密钥管理残留项：**私钥明文存储**（doc/UpdateSecurity.md 已标注，修复不需要轮换公钥）。

**目标**：修复下载超时与脚本健壮性（构成 2.4.5 客户端变更）；publish.ps1 发布自动化；私钥加密；全部有测试/验证闭环，照 doc/UpdateSecurity.md 检查清单发版。

## 3. 方案选型

**整体组织：分层落地**（推荐，理由见下）——
- **立即落地（不等发版）**：D7 私钥加密、B1 publish.ps1。二者都是开发机/仓库操作，不改变客户端行为，提前落地让下次发版直接用上新流程。
- **2.4.5 发版**：仅 A1/A2 两个客户端修复 + README 版本表更新。

- **只修 A 跳过 B/D**：下次发版仍走手工流程，遗漏风险保留。

## 4. 各项设计

### A1 下载超时分级

**现状**：`TextTool.Cli/Program.cs:221` 单一 client（30s）贯穿 `SelfUpdater.UpdateAsync` 全程——API 查询 + 三次 `FetchBytesAsync`（zip/.sha256/.sig）共用。S302 实测 zip 下载约 30s，边缘触发超时（"The request was canceled"）。GUI 检查路径 `AboutTabControl.cs:277` 用 10s，只做 check 不下载，保持不动。

**设计**：查询阶段沿用调用方传入的短超时 client（快速失败）；**下载阶段改用专用长超时 client（90s）**，在 `UpdateClient.Create` 参数化基础上由 `SelfUpdater.UpdateAsync` 内部创建（`using var downloadClient = UpdateClient.Create(TimeSpan.FromSeconds(90))`）。TLS 固定/主机白名单/禁重定向策略天然一致（同一工厂），`MitmDetected` 检测逻辑不受影响。

**取舍**：不采用"统一放宽到 90s"——无网络时 check 失败要等 90s，反馈过慢；分级后 API 错误仍秒级返回，只有大体积下载获得宽限。上限仍在 `MaxDownloadBytes`（256MB）保护内，不引入新风险。

**测试**（TextTool.Tests/UpdateClientTests.cs 扩展）：
- 慢响应 fake HttpMessageHandler：10s 内返回 256KB 响应，短超时 client 失败、90s client 成功
- 现有下载链路测试不回归

### A2 替换脚本 wait-loop 健壮化

**现状**（`TextTool.Core/SelfUpdater.cs:64-73`）：

```bat
:waitloop
tasklist /fi "PID eq {{parentPid}}" >nul 2>&1
if %errorlevel%==0 (
    timeout /t 1 /nobreak >nul
    goto waitloop
)
```

**两个缺陷**：
1. `timeout` 裸命令：PATH 含 Git/usr/bin 时被 GNU timeout 遮蔽，`/t` 参数非法退出非零 → 父进程还在 → 无限空转，替换永远不会发生
2. 无限循环本身：父进程退出后 PID 被复用则永久循环（竞态）

**设计**：循环上限 + 绝对路径：

```bat
set /a tries=0
:waitloop
tasklist /fi "PID eq {{parentPid}}" >nul 2>&1
if %errorlevel%==0 (
    set /a tries+=1
    if %tries% LSS 30 (
        %SystemRoot%\System32\timeout.exe /t 1 /nobreak >nul
        goto waitloop
    )
)
robocopy "{{staging}}" "{{target}}" ...
```

30 次后即使父进程仍在也继续（`robocopy` 失败会由后续检查兜底；文档建议的"循环加次数上限后继续"即此意）。注意 `%errorlevel%` 与 `set /a` 在同一括号块内的延迟展开问题——`set /a` 不触发 `%errorlevel%` 重估，需在块内用 `if !errorlevel!` 或把 `set /a` 放块外结构，实施时以实测为准（生成脚本的单元测试可校验最终文本）。

**测试**（SelfUpdaterTests 扩展）：
- 生成脚本文本含 `%SystemRoot%\System32\timeout.exe` 与计数上限逻辑
- 现有脚本生成测试不回归

### B1 `scripts/publish.ps1` 发布自动化

**目的**：把 doc/UpdateSecurity.md「发布流程」5 步固化成一条命令，强制检查清单。

```
.\scripts\publish.ps1 -Version 2.4.4 [-SkipUpload] [-Force]
```

流程：
1. 参数校验（版本号格式 `v?(\d+\.\d+\.\d+)`）
2. `gh release download` 下载三件套 zip + .sha256 到临时目录（校验 .sha256 存在）
3. 离线签名：`tools/ReleaseSigner sign`（私钥默认 `E:\WorkZone\ApiKey\TextTool-signing.priv.pem`，可用参数覆盖；passphrase 经 `TEXTTOOL_SIGN_PASSPHRASE` 环境变量）
4. `ReleaseSigner verify` 自检，失败即退出（exit 1），**先验证后上传**
5. `gh release upload` 上传 .sig（`.sig` 已存在时：默认报错提示用 `-Force` 覆盖——防误传）
6. 打印检查清单：□ zip □ .sha256 □ .sig verify 通过 □ 待执行：本地真实 update 冒烟

**前置**：gh 在 PATH；ReleaseSigner 已构建（脚本内 `dotnet build tools/ReleaseSigner -c Release` 惰性构建）。

**`-SkipUpload`（dry-run）**：只走到 verify，用于演练/签名验证，不上传。

## 7. 实施记录（2026-09-29）

A1/A2 落地时发现：**A2 的真实根因与本规格 §4 的假设不同**，本节的实测结论优先于 §4 的设计描述。

实测出三处独立缺陷，全部位于同一个替换脚本：

| # | 缺陷 | 实测证据 |
|---|---|---|
| 1 | **脚本以 LF 落盘且含中文时 cmd 解析错位**，会把行从中间劈开 | `setlocal DisableDelayedExpansion` 被拆成 `'xpansion' 不是内部或外部命令`；同一脚本改 CRLF 后正常。这正是 `.gitattributes`/`.editorconfig` 要求 LF 与批处理必须 CRLF 的冲突 |
| 2 | **`tasklist` 的退出码不能当存活判据**——对本机不存在的 PID 也返回 0 | `if %errorlevel%==0` 恒真，循环永不退出；改用 `find` 查输出里有无该 PID |
| 3 | 裸 `timeout` 被 PATH 上的同名命令遮蔽 | 本机 `E:\WorkZone\ClaudeCode\tools\git\usr\bin\timeout.exe` 排在 System32 之前，收到 `/t` 立即报错返回 |

§4 只识别出缺陷 3（并把症状描述为"无限空转"，方向正确但漏了前两条），且假定的"父进程退出即跳出循环"在本机并不成立。

配套改动：等待上限从无改为 30 次；`tasklist`/`timeout`/`find` 一律走 `%SystemRoot%\System32` 绝对路径；
脚本改以 CRLF 落盘。新增 4 条测试：2 条真实执行生成的 .cmd 并断言"替换是否真的发生"（活 PID 仍完成替换、
PATH 上伪造的 timeout 未被调用），1 条钉住 CRLF 不变量，1 条断言下载不受查询 client 短超时约束。
按仓库既有约定，只写文本断言是不够的——缺陷 1/2/3 全都藏在 cmd 的运行时语义里，文本断言一条也抓不住。
